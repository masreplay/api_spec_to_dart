# swagger_to_dart 6.0.0 + postman_collection 1.0.0: any API spec in, typed Dart out

Date: 2026-10-03 · Branch: `feat/v6-postman`

## Goal

The maintainer asked (2026-10-02): read Postman's collection schema on their
own website and the OpenAPI (Swagger) schema, then "write something to 100%
convert it with our tool to support all edge cases, don't do manually",
publishing `postman_collection` if needed. Issue #38 states the goal:
"Postman collection → Dart models and API clients".

Interpretation, decided without further questions (the maintainer asked for no
more questions):

1. **Postman collections become a first-class input of swagger_to_dart.** Every
   official Postman format converts automatically into OpenAPI, which feeds the
   existing generator to produce models and Retrofit clients. Nothing is
   hand-converted.
2. **The official schemas drive the work.**
   - The typed Postman models are *generated by our own tool* from Postman's
     official JSON Schema, replacing the hand-written ones.
   - Converter output is *validated against the official OpenAPI schema*.
   - Inputs are *validated against the official Postman schema*.
3. **Generator gaps are fixed, not worked around.** Generating the official
   Postman schema exposed real OpenAPI/JSON Schema gaps (spike in this
   session):
   - `oneOf` with a string variant becomes an empty class, which loses data.
   - Array components become empty classes.
   - Inline objects become `Map<String, dynamic>`.
   - Swagger 2.0 and YAML input are not supported.
   - Custom HTTP methods do not compile.

   All of these are fixed in the generator, so plain OpenAPI users benefit too.

## Sources read (official)

| Source | What |
|---|---|
| schema.postman.com | Collection JSON Schemas v1.0.0, v2.0.0, v2.1.0 (draft-07), all "stable" |
| learning.postman.com `collections-schemas` | Current app format is **v3.0.0**: a YAML tree (`*.request.yaml`, `.resources/definition.yaml`, `*.example.yaml`) |
| postmanlabs/postman-plugin `skills/collection-schema-v3` | Field-level v3 reference (`$kind` http-request / http-example / collection, other protocols) |
| learning.postman.com `sync-specifications-reference`, `generate-specifications`, `collections/overview` | Postman's own collection → OpenAPI rules (path-level params, first-query-wins, only user headers, OpenAPI 3.1 + JSON Schema 2020-12, webhooks folder) |
| spec.openapis.org | OAS 2.0 (2017-08-27), 3.0 (2024-10-18), 3.1 (2026-08-03), 3.2 (2026-08-30) JSON Schemas; 3.2 adds `query`, `additionalOperations`, `in: querystring`, `itemSchema` |

Copies of the official schemas are vendored as test assets, unmodified. The
validator strips `dependentSchemas` at load time because `json_schema` 5.2.2
cannot compile it. That keyword only checks parameter `style`/`explode`
combinations.

## Architecture

```
input (file | URL | directory; JSON | YAML)
  └─ loadSpec()                         swagger_to_dart/lib/src/input/
       └─ detect format
            ├─ OpenAPI 3.0/3.1/3.2  ─────────────────────────┐
            ├─ Swagger 2.0          → swagger2ToOpenApi()     │
            ├─ JSON Schema doc      → jsonSchemaToOpenApi()   ├─▶ OpenApi.fromJson → generator
            ├─ Postman v1/v2.0/v2.1 → postmanToOpenApi()      │   (models + Retrofit clients)
            └─ Postman v3 directory → postmanToOpenApi()  ────┘
                                       (package:postman_collection)
```

- `loadSpec` is the only entry point, shared by the CLI and the test fixtures.
  Fixtures go through exactly the code users run.
- `postman_collection` holds everything Postman-specific: normalizing v1, v2.0
  and v3 to v2.1, the converter, schema inference and the typed models. It has
  no dio, retrofit or `swagger_to_dart` dependency, so `swagger_to_dart` can
  depend on it. `dart:io` is used only by `package:postman_collection/io.dart`,
  which reads v3 directories. The main library stays web-compatible.
- The converter works on raw JSON maps with lenient accessors. Real exports
  break the schema (unknown auth types such as `jwt`, null header values,
  headers given as strings), and the converter must not throw on any of them.

## Postman → OpenAPI mapping (v2.1 after normalization)

Output is `openapi: 3.1.1`. It becomes `3.2.0` only when some request uses
`QUERY` or a method outside the 3.1 set.

| Postman | OpenAPI |
|---|---|
| `info.name` / `version` (string or `{major,minor,patch,identifier}`) / `description` (string or `{content}`) | `info.title` / `version` (default `1.0.0`) / `description` |
| collection `variable[]` | Resolves `{{var}}` in URLs, headers and bodies. Values become examples and server defaults |
| URL origin (`protocol://host:port`, `{{baseUrl}}`) | `servers`: the most frequent origin, or `{baseUrl}` with a variable default. Operations on another origin get operation-level `servers` |
| URL path segments; `:id` and `{{id}}` segments | path `/users/{id}`; trailing slash kept; duplicate names get suffixes |
| item (request) | One operation. `summary` is the item name. `description` comes from the request, else the item. `operationId` is the camelCased name, unique, and falls back to method + path when the name has no ASCII |
| item-group (folder) path | `tags: ["Parent / Child"]` plus document `tags` with descriptions. Root requests are untagged |
| folder named `Webhooks` (3.1) | `webhooks` |
| same method and path in several items, or an example's `originalRequest` | Merged into one operation. Parameters, bodies and responses are unioned and their samples merged. The first item names it |
| `url.query[]` (disabled too) | `in: query`, optional. A repeated key becomes an array with `explode`. Null or empty keys are skipped |
| `url.variable[]` | Path parameter description and example. `type` (string/number/boolean) becomes the schema |
| headers (array or `"K: V\n"` string) | `in: header`, optional. `Content-Type`, `Accept`, `Authorization`, `Cookie` and transport headers (`Host`, `Content-Length`, `User-Agent`, `Accept-Encoding`, `Connection`, `Postman-Token`, `Cache-Control`) are excluded or mapped elsewhere. `Cookie` becomes `in: cookie` |
| `body.mode=raw` + language/`Content-Type` | JSON (after stripping `//` and `/* */` comments and substituting bare `{{var}}`): media type with an inferred schema and the example. Other text: `{type: string}` under its media type |
| `body.mode=urlencoded` | `application/x-www-form-urlencoded` object with properties, values inferred |
| `body.mode=formdata` | `multipart/form-data`. `text` parts are inferred. `file` parts are `{type: string, format: binary}`, or an array of those when `src` is an array. Per-part `contentType` becomes `encoding` |
| `body.mode=file` | `application/octet-stream` (or the `Content-Type` header) as binary |
| `body.mode=graphql` | `application/json` `{query: string, variables: <inferred>, operationName?}` |
| body `disabled` / `null` | No request body |
| saved example (`response[]`) | Status from `code`, else the reason phrase in `status`, else `default`. Media type from the `Content-Type` header, else `_postman_previewlanguage`, else sniffed. The schema is inferred and merged per status and media type. `examples` are keyed by example name. Response headers exclude transport headers |
| no saved example | `default: {description: Default response}` |
| `auth` on the collection, folder or request (inherited; `noauth` gives `security: []`) | `securitySchemes`: basic, bearer and digest use `http`; `jwt` is bearer with `bearerFormat: JWT`; apikey uses `apiKey` with key name and `in`; oauth2 maps flows, URLs and scopes. oauth1, hawk, awsv4, ntlm, edgegrid and other types use `http` with the scheme name. **Secret values (passwords, tokens, client secrets, keys) are never copied** |
| dynamic variables `{{$guid}}`, `{{$timestamp}}`, `{{$randomInt}}`, … | A sample of the right type (uuid string, integer, ISO date-time, email, boolean, …) |
| `event`/scripts, `protocolProfileBehavior`, `proxy`, `certificate`, cookies, `responseTime`, `timings` | Not representable in OpenAPI, or client config or secrets. Intentionally dropped; the coverage test lists each one |

Coverage proof: a test walks every property path of the official v2.1.0
schema and asserts it appears in the converter's coverage table, as either
mapped or dropped with a reason. A schema path missing from the table fails
the test.

### Schema inference (JSON samples → JSON Schema 2020-12)

- null only → `{}` (any); null alongside other values → those types plus `"null"`.
- Booleans, integers and numbers map directly; integers mixed with numbers become `number`.
- Strings get `format: date-time` only when every sample parses as an ISO 8601
  timestamp with a time part. No other format is inferred (date-only values
  would not round-trip through `DateTime`).
- Arrays: items are the merged schema of all elements; an empty array has items `{}`.
- Objects: properties are the union of keys, values are merged and **nothing is
  required**, as in Postman's own generator (its docs say "required" is added
  by hand). Keys that are all numeric, UUIDs or dates give `additionalProperties`.
- Different JSON kinds give `oneOf`, one variant per kind.
- Every schema stays inline. The generator names nested models by context
  (G1), so there are no hoisted components to dedupe.

### Other inputs

- **v2.0:** auth objects (`{basic: {username, password}}`) become v2.1
  attribute arrays.
- **v1:** requests, folders and order arrays, `dataMode` (params, urlencoded,
  raw, binary, graphql), `headers` strings, `pathVariables` and v1 responses
  all become v2.1. Implemented from the official v1 schema.
- **v3 directory:**
  - `definition.yaml` (name, description, variables, auth, `order`) becomes
    the collection or folder.
  - `*.request.yaml` (`http-request` fields: url, method, headers,
    queryParams, pathVariables, body `{type, content}` for json, text, xml,
    html, javascript, formdata, urlencoded, file and none, plus auth) becomes
    an item.
  - `*.example.yaml` (`response {statusCode, statusText, headers, body}`)
    becomes saved responses.
  - `graphql-request` becomes POST with a graphql body.
  - grpc, websocket, socket.io, mqtt, mcp and llm requests are skipped with a
    warning, since they are not HTTP.
  - Ordering uses `order`, then the name.
  - Multi-auth keeps the first entry.
- **Postman API envelope** `{collection: {...}}` is unwrapped.
- **Swagger 2.0:** converted to OAS 3.0 (swagger2openapi semantics):
  - `definitions` become schemas; `parameters` and `responses` move to
    components with refs rewritten.
  - `body` and `formData` become `requestBody`.
  - `consumes`/`produces` become media types.
  - `host`, `basePath` and `schemes` become `servers`.
  - `securityDefinitions` become `securitySchemes`.
  - `type: file` becomes binary.
  - `x-nullable` becomes `nullable`.
  - `collectionFormat` becomes `style`/`explode`.
- **JSON Schema document** (`definitions` / `$defs`, any draft):
  - Definitions become `components.schemas`, named by **key**: definition
    titles are dropped because JSON Schema titles are labels.
  - The root becomes a component named by its `title`, else the input file
    name (Postman's `collection.json` gives `Collection`).
  - `#/definitions/x`, `#/$defs/x` and `#` refs are rewritten.
- **YAML**: `.yaml`/`.yml` files and YAML URL responses are parsed for every
  format.

## Generator changes (swagger_to_dart)

| # | Change | Before |
|---|---|---|
| G1 | Inline object schemas with `properties` become freezed models, named by title (unless it clashes with a component or a different model) or context. Contexts: property `${Class}${Prop}`, array item `…Item`, map value `…Value`, body `${Method}Body`, response `${Method}Response`, parameter `${Method}${Param}`, union variant `${Union}${Case}Value` | `Map<String, dynamic>` |
| G2 | `oneOf`/`anyOf`/type arrays that mix JSON kinds, with at least one array or object variant, become a sealed union. `fromJson(Object? json)` switches on the JSON kind (String, int, double/num, bool, List, Map), then on discriminator or keys inside Map. Case names are `string`, `integer`, `number`, `boolean`, `list`, `object`, or the ref name. An object variant whose properties share a `const` property with distinct values gets an inferred discriminator. Primitive-only mixes stay `dynamic` | `dynamic`, or an empty class for components |
| G3 | Components that are not object models (array, primitive, map, `$ref` alias) become `typedef Name = DartType;` | Empty freezed class (data loss) |
| G4 | Output with no operations has no `api_client/`. `models/exports.dart` exports dio and the `MultipartFile` converter only when a model uses `MultipartFile` | Always both |
| G5 | Clients are grouped per operation tag, not per path | Every operation on a path was copied into each of its tags' clients |
| G6 | `trace`, `connect`, OAS 3.2 `query` and `additionalOperations` use `@Method('X', path)`. The bogus `pat` method is removed | `@TRACE` etc. do not exist, so the output did not compile |
| G7 | Operation- or path-level `servers` give an absolute URL in the annotation (dio skips `baseUrl` for absolute paths) | Ignored |
| G8 | `model.class_prefix` config prefixes every generated model class (component and inline) | None |

## postman_collection 1.0.0

- `lib/postman_collection.dart` (pure Dart):
  - `PostmanCollection` and the other typed models, generated by
    swagger_to_dart from the vendored official v2.1.0 schema with
    `class_prefix: Postman`. Committed, checked for drift in CI.
  - `normalizePostmanCollection(json)` turns v1, v2.0 or v2.1 into v2.1.
  - `postmanCollectionFromV3Files(Map<String path, String yaml>)` reads v3.
  - `postmanToOpenApi(json)` converts.
  - `isPostmanCollection(json)` detects.
  - `inferJsonSchema(samples)` infers schemas.
- `lib/io.dart`: `readPostmanCollectionDirectory(path)` for v3 directories.
- The old hand-written models, `PostmanCollectionDocumentationMixin` and the
  dio/retrofit request-capture helpers are removed from the package. The
  example app keeps a dio interceptor recipe that builds `PostmanItem`s from
  `RequestOptions` with the new models, so the capability is still there
  without forcing dio on the converter's users.
  (Pub has no optional dependencies, and swagger_to_dart must not pull dio
  and retrofit through it.)
- pubspec: the repository points to this monorepo. The package is currently
  discontinued and unlisted on pub.dev; this release reinstates it.

## Verification

- **TDD throughout:** each mapping row, inference rule and G-change starts as a
  failing unit or golden test.
- **postman_collection:**
  - Unit tests per mapping row.
  - Goldens: every fixture collection's OpenAPI output.
  - Every golden output validates against the official OAS 3.1/3.2 schema, and
    every fixture input against the official Postman schema of its version.
  - Generated models round-trip each fixture: `toJson(fromJson(x))` equals `x`
    projected onto the official schema. Keys the schema does not define are
    ignored, and so are nulls and schema defaults that the models add for keys
    absent from `x`.
  - The coverage test.
- **swagger_to_dart:**
  - Golden fixtures may provide `openapi.json`/`.yaml`, `swagger.json`
    (2.0), `schema.json` (JSON Schema) or `collection.json` / `collection/`
    (Postman).
  - The official Postman v2.1 schema is itself a fixture (`json_schema_postman`).
  - New fixtures cover G1 to G8.
  - The e2e harness compiles every fixture.
  - For Postman fixtures it **auto-generates** round-trip tests: every saved
    JSON example decodes with its generated response model and re-encodes to
    a fixpoint.
- **CI:**
  - The core job adds postman_collection tests.
  - A new `postman_models` job regenerates the typed models and fails on drift.
  - pana scores both packages and must stay at the maximum.
  - The example drift job is unchanged.

## Versions, breaking changes, release

- **swagger_to_dart 6.0.0** is breaking in generated output:
  - G1: inline objects become classes.
  - G2: mixed unions become sealed classes.
  - G4: exports change.
  - G5: methods can move between clients.
  - G6: methods get new annotations.

  G3 and the rest are fixes or additions. CHANGELOG migration notes cover
  each break.
- **postman_collection 1.0.0** is a breaking rewrite. The package was
  discontinued and has no dependents, so the risk is low.
- **Release:** PR → CI green → merge. Publish postman_collection 1.0.0 first,
  because swagger_to_dart depends on it, using `dart pub publish` with local
  credentials as the maintainer asked. Then tag `v6.0.0` and let the publish
  workflow release swagger_to_dart.

## Out of scope

- Non-HTTP Postman protocols (gRPC, WebSocket, Socket.IO, MQTT, MCP, LLM).
- Scripts and tests.
- Postman environments (variables stay server variables).
- Structural dedupe of identical inferred shapes across operations.
- Generating Postman collections from OpenAPI (the reverse direction).
